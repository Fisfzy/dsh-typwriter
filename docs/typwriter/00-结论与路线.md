# Texpile → DSH 插件：可行性结论与路线

> 结论基于对 `texpile` 源码的只读分析（`D:\AIWORK\TYPST PAPER WRITE\texpile`）、本机 DSH 0.2.2-rc.1 发行包与源码 checkout `C:\Users\Fisfzy\dsh-harness`，以及本机已有插件实测。
> 三份详细取证报告：`reports/typst-editor.md`（Texpile Typst 栈）、`reports/agent-bridge.md`（MCP/ACP/许可）、`reports/dsh-plugin-fit.md`（DSH 侧适配）。

---

## 一、一句话结论

**不困难，但"困难的那一部分"恰好是 Texpile 的招牌——可视化（WYSIWYG）编辑器。**
把它拆成两件事就清楚了：

| 你要的东西 | 难度 | 工期量级 |
|---|---|---|
| **A. agent 能写/改/编译/出片 Typst 论文**（结构、诊断、导出、事务写入） | **容易~中等** | 2~4 周 |
| **B. 人在 DSH 里用 Texpile 那套可视化 Typst 编辑器** | **困难** | 1~2 个月 |
| **C. 一条配置就接上 Texpile（不写代码）** | **极简单** | 半天 |

关键判断：**agent 不需要 WYSIWYG**（agent 改的是源码文本），WYSIWYG 是给人看的。所以"对 DSH agent 友好化"这个诉求，落在 A 段——也就是便宜的那一段。

---

## 二、为什么是这个结论（三个决定性事实）

### 1. Texpile 的 Typst 能力，真正的底座是 tinymist，不是 Texpile 自己

- 语法解析：`packages/typst-syntax-wasm` —— Typst 官方 `typst-syntax` 0.15 编译成 WASM，**273,547 字节**，仅 1 个 import，无 DOM/WASI 依赖，`pkg/` 已入库（免 Rust 工具链），**package.json 声明 Apache-2.0**。
- 编译/LSP/预览/导出：全部外包给 **tinymist** 二进制（`typstService.ts` 只是 `spawn('tinymist',['lsp'])` + 自实现 `Content-Length` 分帧，**纯 Node，零 Electron 依赖**）。
- 实时预览：**不是自研渲染**，而是把 tinymist 内置预览页抓回来、改 websocket 地址、注入主题，再 loopback 重发 + iframe。

→ 结论：**agent 要的"能编译、能读诊断、能出图"，DSH 直接用 `tinymist compile` / `tinymist.exportPng` 就能拿到，跟 Texpile 无关。** Texpile 在 agent 这条线上不可替代性很低。

### 2. 唯一"贵"的是可视化编辑器，而它比看起来更贵

| 项 | 实测 |
|---|---|
| Typst 专属可视化代码 | 289 文件 / **12,811 行** |
| 4 跳依赖闭包（实测，仍非完整） | **540 文件 / 36,041 行**（含 `$lib/editor/visual` 119 文件、`languages/latex` 40 文件共享代码） |
| 通用视觉编辑层 `$lib/editor/visual` | 实际代码约 **27,000 行** |
| MathLive fork（Typst 公式编辑） | 192 文件 / **63,294 行** |
| UI 层 | 15 个 Svelte 5 组件，与宿主主题/runes 交织 |

**这不是"复制目录"，是"连通用编辑器层一起搬"。** 且 DSH 官方明确反对用 iframe 装宿主页面（丢主题 token / locale），要求"插件 UI 就是宿主 UI"，所以连 iframe 兜底都被堵掉。

好的一面：写回 `.typ` 本身**不耦合** —— serializer → DocumentBuffer → 通用 FileWriter。以及宿主移植的接缝是**干净的单点**：整个平台依赖就是 `window.texpileNative` 这一个对象（`fileSystem.ts:238-241`），渲染层本身是 Svelte + ProseMirror + CodeMirror 的浏览器代码（仓库甚至已有 `build:web` 走 Vite 出 web 版）。所以"搬"是可能的，只是量大。

### 3. Texpile 的 MCP 服务器**不能 headless**（这是最容易踩的坑）

- 唯一传输是 loopback HTTP（`127.0.0.1:7317`，dev `7318`），Streamable HTTP + stateless，**全仓 0 处 stdio transport**。
- `McpHost` 直接以 `BrowserWindow` 为输入；**无窗口时 17 个工具里 16 个返回 `no matching Texpile window`**。
- Windows/Linux 关最后一个窗口即退出进程 → 端口没了。
- 仓库无任何 `bin` 入口、无 CLI、无 daemon 模式；`helper/` 是 utilityProcess，`draftDaemon` 是 App 内暖 lualatex，都不是对外服务。

→ **不能把 Texpile 当成 DSH 的后端引擎。它只能在"人开着它、并且正看着某个窗口"时提供编辑器遥测。**

## 三、三条路线（按投入排序，可叠加）

### 路线 C：MCP 直连 —— 半天，零代码（推荐先做，验收价值）

DSH 原生支持挂 MCP server（`save_capability(kind="mcp", transport="streamable-http", url=...)`）。
Texpile 文档给的地址就是 `http://127.0.0.1:7317`。

- **得到**：`get_editor_state` / `get_unsaved` / `open_file` / `set_view_mode` / `show_diff` / `comments` 系列 —— 也就是"agent 知道用户正在看哪一行、有没有未保存改动"，避免写盘与 buffer 冲突；以及"把结果指给用户看"。
- **限制**：要求用户装有 Texpile 并开着（本机当前**未安装**，端口 7317 不通）；MCP 默认关闭需手动开；启动后 MCP 在 deferred 队列最后才起，刚开几秒会 connection refused，DSH 探活要处理。
- **Typst 坑**：`get_editor_state.livePreview` / `get_compile_config` / `compile` 三处读的是 **LaTeX 车道**（`compileConfig.current.latex.liveMode`），而 Typst 自己的开关是 `typst.preview`。对一个默认配置的 Typst 项目，agent 会被系统性误导成"有 shell 编译在跑"，而 `get_diagnostics` 读的 `.log` 在 Typst 默认 Preview 模式下**根本不写** → 返回空或陈旧数据。**这条必须在 DSH 侧规避（自己去跑 `typst compile` 读 stderr），不要信 `get_diagnostics`。**
- **许可**：仅 MCP 调用 = 无 AGPL 义务。

### 路线 A：DSH 原生 Typst 工作台 —— 2~4 周（主体工程，推荐）

不搬 Texpile 的 Electron 层，**只借它的可移植件与设计**：

| 组件 | 来源 | 难度 |
|---|---|---|
| 语法高亮/折叠/大纲 | `packages/typst-syntax-wasm`（Apache-2.0，换 loader 即可） | 容易 |
| tinymist 进程 + LSP 分帧 | `electron/src/typstService.ts`（230 行，删掉计时器/userData 即可） | 容易 |
| 编译命令拼装 | `workspace/typstCommand.ts`（169 行纯字符串逻辑） | 容易 |
| 导出 PDF/PNG/SVG/HTML | `languages/typst/export/`（841 行，纯逻辑） | 容易 |
| 编译编排/事务/回滚/SSE 日志 | **照抄本机 `dsh-paper-desk`**（已 294 测试 + 真机 E2E） | 容易 |
| PDF 面板 | pdf.js + 前缀路由（注意 `content-type: text/javascript`、cmaps、standard_fonts） | 容易 |
| `typst_*` agent 工具 | `ctx.tools.register()`，参照 paper-desk 13 个 / tylina 27 个 | 容易 |
| tinymist IntelliSense（补全/诊断/hover） | **自建**：`ctx.subprocess.spawn(stdio pipe)` + WS 桥 + CodeMirror `lsp-client` Transport | 中等 |
| 实时预览 | **走 `typst compile` → PDF + pdf.js 热刷新**（不要抄 Texpile 的 tinymist 预览页，随版本碎） | 中等 |

**已确认的 DSH 宿主能力**：`ctx.fs`、`ctx.subprocess`（stdio pipe + pty）、`webServer.register` + `registerUpgrade`、sessionProjections、storage、configEditor 全都有；**唯一缺口是 LSP**（0.2.2-rc.1 发行包 0 个 lsp 包，源码里的 `ctx.lsp` 只有 4 个导航操作、无 completion/diagnostics）→ 必须自建 LSP 客户端与传输。

**UI 扩展点全部是公开的**：主区整页（`main` keyed slot）、左侧栏入口（`sidebar.panellist`，id 必须等于 main 的 key）、右侧栏 tab（`sidebarRightTabs` + `sidebar.right.pane.tab` 两段式）、设置分区，已有两个跑通先例。

**四条会绊住实现的硬约束**（容易踩，提前知道能省几天）：
1. 插件清单**只认 `package.json` 的 `dsh` 字段**；`dsh-plugin.json` / `dsh.plugin.json` 在 0.2.2-rc.1 已是死格式（对 213MB asar 二进制全量扫描，两个字符串各命中 **0 次**）——`ego-browser`、`dsh-better-sidebar` 里那两份是 0.1.x 遗留，别照抄。
2. `/plugins/<pkg>/assets/*` **只收图片**；wasm / 字体 / pdf.worker / cmaps 必须自己挂 prefix 路由。
3. 插件自有路由会**绕过 `/api` 信任栅栏**，须自校验 `dsh-auth-*` cookie。
4. bundle 是一个 `window.__ModuleLoader__.load({id, factory})` 的 CJS 文件；`ctx.subprocess` 的 `stdio: 'pipe'` 文档里明写就是给 LSP JSON-RPC 用的。

### 路线 B：把可视化编辑器搬进来 —— 1~2 个月（最后做，且建议重写而非搬运）

要付的代价：12.8k 行 Typst 专属 + ≥36k 行依赖闭包 + Svelte 5 运行时 + MathLive（63k 行）。
**建议的姿态**：以 `typst-syntax-wasm` 为唯一语法真相，**在 DSH 内重写一层薄的 ProseMirror 宿主适配**，只复用 Texpile 那三个"纯转换"目录（`schema.ts` / `convert/**` / `serialize/**`，约 2.1k 行）。不要去搬 `$lib/editor/visual` 整包。

## 四、对 DSH agent 友好化的具体改造清单

Texpile 现有 MCP 面 = 「编辑器遥测 + 视图方向盘 + 评审意见簿 + 单点建议」。它刻意把"写文件、编译、读源码"留给 agent 自己的工具。对"无人盯屏的 Typst 论文写作 agent"，缺口集中在 5 条，也正是要改造的地方：

1. **无头能力 = 0** → DSH 侧自带 `typst compile`，不依赖 Texpile 窗口。
2. **没有 Typst 结构/大纲/语义查询**（编辑器里其实**有** `typstOutline()` 实现，只是**没有 MCP 出口**）→ DSH 应暴露 `typst_outline` / `typst_query`（查 `<label>`、`@cite`、图表清单、页数）。
3. **Typst 诊断被 LaTeX 假设污染**（见路线 C 的坑）→ 自己解析 `typst compile` 的 stderr，别用 `get_diagnostics`。
4. **没有 Typst 导出**（能力在，但落地走原生 `dialog.showSaveDialog`，无人值守无法导出）→ DSH 走 `tinymist.exportPng/Pdf`。
5. **写入口太窄**：`suggest_edit` 只能改**已打开的那一个文件的、逐字命中的、一次一处**，且只做 LaTeX 语义校验（`@cite`/`<label>` 无守卫）；无批量版、无 undo 出口 → DSH 用"唯一写入口 + 备份 + 回读校验 + 编译失败回滚"的事务模型（paper-desk 已跑通）。

另外两条可直接抄的工程经验：
- DSH **不能新增 session event type**（会被会话重开校验拒绝），批注数据模型必须自建（项目内状态文件 + 自建路由 + 浮层 UI）。
- DSH 会话注入的契约是 `{ content, source }`，**不能带 `role`**，否则会话日志写坏、整条会话打不开。

## 五、许可（重要，决定能不能分发）

| 做法 | AGPL 是否覆盖你的产物 | 你要做的事 |
|---|---|---|
| (a) 只走 MCP | 否 | 无需 Texpile 许可；可事实性声明"支持 Texpile" |
| (b) vendor / fork 代码 | **是** | 整插件 AGPL-3.0 + 提供源码（含 §13 网络条款）+ 保留声明 + **改名换图标并注明衍生**（`TRADEMARK.md` 禁止使用其名称/logo，否则需商业授权） |
| (c) 只用两个包 | 否（MIT / Apache-2.0） | 保留版权与许可文本；Apache 侧标注修改；不用其商标 |

- 仓库整体 **AGPL-3.0**；`packages/mathlive` = MIT，`packages/typst-syntax-wasm` = 清单声明 Apache-2.0（但**无独立 LICENSE 文件**，建议取书面确认）。
- 唯一"非宽松"第三方依赖：cspell 拼写词典（`it`/`pt-BR` 为 GPL-3.0-or-later，`de/es/pt-PT/pl` 为 LGPL-3.0）—— **不要一起打包**。

→ **推荐停在 (a) + (c)**：只走 MCP、只复用两个宽松包，避开 AGPL 与商标问题，同时拿到绝大部分价值。

## 七、建议的决策

1. **先做路线 C**（半天）：挂 MCP，验收"agent 能感知用户在改哪一行"这一条。它零代码、零许可风险。
2. **主线做路线 A**（2~4 周）：以 `dsh-paper-desk` 为骨架扩出 Typst 工作台，**先做 tinymist（中等）再做 WYSIWYG（困难）**——因为前者能立刻把"agent 能不能读懂/改对 Typst"闭环，后者只服务人。
3. **路线 B 单独立项**，按 1~2 个月估，且用"重写薄宿主 + 只复用 2.1k 行纯转换代码"的姿态，不要整包搬运。
4. **许可上停在 (a)+(c)**，避开 AGPL 传染与商标问题。
