## 一、点击跳转丢失：根因与修复

### 结论
**根因不是 Texpile 的 bug，也不是 Typst 没有同步能力——是我们漏实现了 tinymist 的 LSP 桥。**
这条链断在中间一环，因此"预览能显示、点击没反应"。

### 真正的机制（读代码得出，不是猜）
Typst 没有 SyncTeX，它的"点 PDF 跳源码"完全由 tinymist 提供，路径是：

```
预览 iframe 里点击
  → tinymist 预览页发 websocket：src-point {"page_no":N,"x":..,"y":..}
  → tinymist 服务端解析出源码位置
  → 通过 LSP 向编辑器发请求  window/showDocument {uri, selection:{line,character}}
  → Texpile 的 LSP 客户端接住 → 打开文件并定位到行
```

代码证据：
- 预览页的点击处理 `installEditorJumpToHandler`：`windowElem.typstWebsocket.send('src-point ...')`（tinymist 0.15.12 内置页面，实测抓取到）
- 编辑器侧 `apps/texpile-editor/src/lib/languages/typst/intellisense/lspClient.ts:299-303`（`tinymist/preview/scrollSource`）与 `:487-522`（`window/showDocument`）——注释明写"这正是 tinymist 官方 VS Code 扩展实现点击跳转的方式"

所以我们缺的是 **`texpileTypst.startLsp/send/stopLsp/onMessage`** 这套 LSP 桥（`electron/src/preload.ts:476-496`）。

### 为什么之前完全没反应
两个原因叠加：
1. `texpileTypst` 里没有 `startLsp`，LSP 从没启动 → tinymist 也不存在 → 没有任何人发 `window/showDocument`；
2. 顺带 `synctex` 也没实现（PDF 面板的反向搜索走它）。但即便实现了也没用——Typst 没有 SyncTeX 数据。

也就是说，**之前那一版连智能提示（补全/诊断）也是没有的**，只是不明显。

### 修复（已实现并验证）
新增 `src/host/lsp.js`：
- spawn `tinymist lsp`（绝对路径，宿主 PATH 不含 System32 的坑已绕过）
- 自实现 `Content-Length` 分帧，裸 JSON 字符串双向转发
- 二进制消息/日志走 stderr，不污染协议流

新增 `typst:preview:prepare`：**不重写 tinymist 的预览页**，直接把 iframe 指向 `http://<host>/`。
tinymist 的 data plane 只校验 loopback http 来源，我们的页面正好是，因此无需移植 Texpile 那套
"抓页面 + 替换 websocket 地址 + 注入 bridge + loopback 重发"（那套还依赖 tinymist 私有字段，升级即碎）。

顺带修掉两个时序坑：
| 坑 | 现象 | 修法 |
|---|---|---|
| SSE 未连上时消息丢失 | `initialize` 回包（毫秒级）到达时 EventSource 还没 open → 客户端永久等待，预览"正在连接" | shim 在 `startLsp` 前 `await` 总线就绪；宿主侧额外缓存未投递帧并补发 |
| 陈旧帧污染新会话 | 页面重载后把上一轮的 `initialize` 回包补发给新客户端 → 握手错乱、预览起不来 | `typst:lsp:start` 前清空所有 `typst:lsp:*` 缓存帧 |

### 验证
- LSP 隔离测试：`initialize` → tinymist 正常回包（capabilities 齐全）
- 页面内实测：点击预览封面文字 **单点** → 收到 `window/showDocument`（`selection.line = 67`）→ 编辑器标题从 `main.typ` 变为 **`cover.typ`**
- 同时收到 `tinymist/documentOutline` 通知 → 大纲/智能提示链路也通了
- 预览渲染 97 页（96 个页面 canvas），中文正常

## 二、默认 AI 助手改为 DSH（已配置并验证协议）

### 关键发现：DSH 自己就是 ACP 服务端
DSH 随发一个 **`acp` profile**（`@deepseek-ai/dsh-acp`），`dsh --profile acp` 直接提供标准 ACP v1 stdio 服务，
且**会话工作区由 ACP 客户端传入**——正好是论文目录。

而 Texpile 的 Agent 面板支持 `custom` 自定义 ACP 命令（`electron/src/ai/acp/acpAgents.ts`，设置键 `agentPanel` / `agentPanelCommand`）。

所以"把默认 AI 助手换成 DSH"不需要写适配器。

### 已写入的设置
```json
{
  "agentPanel": "custom",
  "agentPanelCommand": "node C:\\Users\\Fisfzy\\.dsh\\typwriter\\acp-filter.mjs --profile acp",
  "aiOff": false
}
```

### 为什么要那个过滤器（acp-filter.mjs）
实测 `dsh --profile acp` 的 **stdout 混进了一行普通日志**：
```
[dsh-model-follow] active: ordinary sessions route on the live deployment default model
```
来源是用户级 `~/.dsh/cordis.patch.yml` 给所有 profile 注入的插件。ACP 客户端按 ndjson 逐行 `JSON.parse`，
一行垃圾就可能让整个会话失败。

`acp-filter.mjs` 只做一件事：stdin 原样转发给 dsh，**stdout 里只放行能 `JSON.parse` 成对象的行**，其余改投 stderr。
实测结果：`clean=1 dirty=0`，`initialize` 干净通过（`agentInfo: deepseek-harness-acp v0.0.1`）。

> 备选（未采用）：直接改 `~/.dsh/profiles/acp/cordis.patch.yml` 禁用该插件——但那样会动你现有的 profile 装配，
> 影响其他会话；过滤器只作用于这个入口，零副作用。

### 附带好处（这点很重要）
Texpile 的 Agent 面板**每条消息会自动带上当前打开的文件或选中的行**（`docs/ai-assistant/agent-panel.md`）。
把面板接到 DSH 之后，"在论文里选中一段 → 直接问 DSH"这个最常用的动作就**自动可用**，不需要另做选区桥。

## 三、DSH 功能 × 论文编辑：怎么结合

### 现状与抓手
插件宿主侧是一个完整 Node 进程，手里有三样东西：
1. 论文目录的**真实文件系统**（`fsops.js`）
2. **tinymist LSP 连接**（我们自己在管，可读可写协议流）
3. 浏览器半片里那个 **iframe**（同源，可 postMessage 控制）

### 一个关键技巧：用 LSP 帧反向"驾驶"编辑器
我们已经能往 SSE 里注入 `typst:lsp:message`。而客户端对 `window/showDocument` 只按协议处理、不校验来源。
所以宿主只要推一帧：

```json
{"jsonrpc":"2.0","id":999,"method":"window/showDocument",
 "params":{"takeFocus":true,"uri":"file:///…/body/chapter03-deformation.typ",
           "selection":{"start":{"line":42,"character":0},"end":{"line":42,"character":0}}}}
```

编辑器就会打开那个文件并定位到第 42 行——**不需要改 Texpile 一行 UI 代码**。
这是"DSH 说完话 → 论文跳到对应位置"最便宜的实现，也是本轮最有价值的发现。

### 建议分四步做（按性价比排序）

**第 1 步：把论文能力注册成 DSH 工具（最高价值，1~2 天）**
`ctx.tools.register()` 一组 `typst_*`，让主对话里的 DSH 直接干活：
| 工具 | 作用 | 实现要点 |
|---|---|---|
| `typst_outline` | 章节树 + 每节行号 | wasm 解析或 `tinymist/documentOutline` |
| `typst_read` / `typst_write` | 读写源文件（写前备份、写后回读校验） | `fsops.js` |
| `typst_compile` | 编译并返回诊断 | 复用 `term.js` 的 `tinymist compile` |
| `typst_locate` | 在编辑器里定位到某文件某行 | **注入 `window/showDocument` 帧** |
| `typst_selection` | 用户当前选中/光标位置 | 需要下一步的选区上报 |
| `typst_query` | 查 `<label>` / `@cite` / 图表清单 | `typst query` |

**第 2 步：反向通道——编辑器把状态推给宿主（1 天）**
在 shim 里监听 `window.texpileNative` 之外的东西做不到（应用不广播选区），但可以用注入脚本包一层
`document.addEventListener('selectionchange')`，把 `{file, line, selText}` 定期 postMessage 给父页面，
父页面再 `POST /typwriter/api/state` 落到宿主。这样 `typst_selection` 就有了数据。

**第 3 步：DSH 侧的工作台栏（半天）**
在主区 iframe 上方加一条极窄工具条：`打开论文` / `重新编译` / `在对话中讨论` —— 让人知道这里和 DSH 是一体的。

**第 4 步：把 Texpile 的"建议/批注"接进 DSH（2~3 天，选做）**
Texpile 已有 `suggest_edit`（改动落成建议让作者决定）与 `.texpile/comments.jsonl`（锚定到引文的评论线程）。
可以把它做成 DSH 的 `typst_suggest_edit` 工具：**agent 的措辞改动不直接落盘，而是变成作者可接受/拒绝的建议**。
考虑 DSH 不能新增 session event type，批注数据仍放 `.texpile/comments.jsonl`，DSH 侧只读写不改模型。

### 不建议做的
- 不要在 DSH 里重做 PDF↔源码映射（Typst 无 SyncTeX，tinymist 已是最好的实现）
- 不要把 Texpile 的 WYSIWYG 层再移植一遍（12.8k 行 + 36k 行依赖闭包）
